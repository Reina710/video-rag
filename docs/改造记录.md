# AI视频分析平台（video-rag）改造记录

> 从「能跑的原项目复刻」到「有检索评测、有分段摘要、有单测」的完整记录。
> 按「遇到什么问题 → 怎么改 → 改完什么效果」组织，方便复盘和后续维护。

---

## 总览

一句话：**把一个「能问答的视频 RAG」补成了「知道自己哪里会坏、并且能量化」的系统。**

主要做了四件事：

1. **工程能力**：上传后自动解析、分片上传、健康检查、失败重试
2. **检索质量**：向量 + BM25 → RRF → 扩窗 → rerank，并量化三种配置
3. **时间准确性**：修掉了「点过去和说的不一致」的时间戳错位
4. **长视频覆盖**：5 分钟分段摘要，解决「只看前 5 分钟」的时间坍缩

## 一、环境与依赖（7 个坑）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `docker ps` 报 permission denied | 我的命令被沙箱禁了命名管道，**不是没装 Docker** | 提高权限后正常 |
| 2 | 三个中间件都没起 | 容器存在但停了 | `docker start qdrant redis minio` |
| 3 | anaconda 缺一半依赖 | 项目真正用的是 `ca-test` venv（Python 3.13） | 定位到 `run_web.bat` 里的路径 |
| 4 | `faster-whisper` 报 `metadata_errors` | `av 19` 改了 `open()` 参数，与 faster-whisper 1.2.1 不兼容 | **先用 ffmpeg 抽 16k wav，再把 numpy 数组喂给模型**，彻底绕开 av |
| 5 | `imageio_ffmpeg` 找不到 | 没装 | `_ffmpeg()` 加回退：imageio → 系统 ffmpeg → "ffmpeg" |
| 6 | Qdrant 一直 502 | **Windows 系统代理**把 `127.0.0.1:6333` 也拦了 | 把本地地址写进 `NO_PROXY` |
| 7 | 匿名上传 500 | `videos.user_id NOT NULL`，未登录时是 None | `user_id or 0` 兜底 |

> 第 4 和第 6 是最容易复发的，换机器部署时先检查这两处。

## 二、工程能力（P0）

### 1. 上传后自动解析

**问题**：原项目上传完只是存文件，要手动跑三个脚本才建索引。

**改法**：新增 `pipeline.py`，上传完成自动进后台队列：

```
上传 → 后台线程 → ASR → OCR → 向量化 → Qdrant
                    ↓
              状态写回 videos 表：转写中 → 识别画面文字 → 建向量索引 → 完成
```

- 单线程 + 队列（够用且好讲，不引入 MQ）
- 模型懒加载缓存（484MB，不能每任务重载）
- 失败写 `status=failed` + 原因，不抛给 Web 层

**效果**：前端视频列表实时显示「解析中 / 已就绪 / 失败」。

### 2. 分片上传 + 断点续传

**问题**：大视频一次性 POST 容易超时，断了要重传。

**改法**：5MB 分片，四个接口 `init / chunk / status / complete`；前端先查已传分片，**只补缺的**；每片单独重试（0.5s/1s/2s 退避）。

### 3. 健康检查 / 失败重试 / 上传去重

- `GET /health` 返回 redis / minio / qdrant 状态
- OpenAI 客户端 `max_retries=3`；Qdrant upsert 单独包一层重试
- 文件 SHA256 去重，同一视频重复上传复用已有索引

## 三、多视频隔离 + 检索评测（P0）

### 1. 按 `media_id` 过滤

**问题**：多视频时检索不隔离，问 A 会捞到 B 的证据，**时间戳跳转会跳到错的视频**。

**改法**：全链路打通 `media_id`：

```
前端 askWithVideo() → api { mediaId } → 路由 data.get("mediaId")
  → search(media_id) / run_agent(media_id) → Qdrant Filter
```

**顺手修的两个坑**：
- 缓存键要带 `mediaId`，否则 A 视频的答案会被 B 视频复用
- `/api/ask_agent` 的缓存 **get 和 set 用了不同的 key**，永远命中不了 → 统一

**数据迁移**：现有 455 个向量点 `media_id` 全是 `None`（旧脚本没写），直接加过滤会「一条都搜不到」→ 确认属于哪个视频后**回填**。

### 2. 检索层评测

**问题**：端到端评测只知道答案好不好，**定位不到是检索没捞到还是生成没写好**。

**改法**：新增 `eval_retrieval.py`，用人工标定的**黄金时间区间**单独量检索：

| 指标 | 含义 |
|---|---|
| `hit@K` | Top-K 里有没有落在正确时间区间的证据 |
| `recall@K` | 多区间被覆盖的比例 |
| `MRR` | 第一条命中证据排名的倒数 |

## 四、检索质量（P1）——这里踩了最多的坑

### 坑 1：融合掉点——但根因不在融合 ⭐

第一版测出来是这样，看起来"融合有害、只有 rerank 有用"：

| 配置 | hit@1 | MRR |
|---|---|---|
| 纯向量 | 87.5% | 0.875 |
| + BM25 + RRF | **75.0%** ↓ | 0.750 |
| + rerank | **100%** ↑ | 1.000 |

按"先查最弱那一路，再调融合参数"的顺序排查，发现 BM25 这一路有两个前提是从校园项目直接
照搬、但在视频语料上不成立的：

**① 繁简没统一**

faster-whisper 的中文输出默认是繁体（「我最愛的漫畫」「窮如之下的魔女」），用户提问是简体。

```
文档：我最愛的漫畫      → jieba: [最愛, 漫畫]
查询：作者最喜欢的漫画   → jieba: [作者, 喜欢, 漫画]
```

「漫畫」和「漫画」在 BM25 的倒排里是两个不同的词，字面命中为 0。而 embedding 对繁简不敏感，
所以现象是「向量召得回、BM25 一条都召不回，RRF 把噪声抬进 Top-1」。8 题里 BM25 对正确区间
的召回只有 7/8。

修法：在分词前做繁→简归一（opencc t2s，装不上就原样降级）。

**② 长度归一的假设在 ASR 上不成立**

b=0.75 的假设是"文档越长，命中的词越可能是巧合，要打折"。这条在知识块上成立，
在 2~3 秒的 ASR 行上不成立：语料平均每条只有 **3.77 个词**，长度差异来自**语速**，
不来自信息量。b=0.75 会把「我最愛的漫畫」这种 7 字短句的权重放大 5 倍，压过真正有上下文的片段。

修法：b 从 0.75 降到 0.4。

**修完的对照**（同一 8 题）：

| 配置 | hit@1 | BM25 召回 |
|---|---|---|
| 原样 + b=0.75 | 75.0% | 7/8 |
| 繁简归一 + b=0.75 | 87.5% | 8/8 |
| 繁简归一 + b=0.4 | **100%** | 8/8 |
| 繁简归一 + b=0.4 + 手工权重 2:1 | 87.5% | 8/8 |

最后一行是顺手做的反证：**两路都修好之后，手工给向量加权反而掉点**。融合参数不是调出来的，
是两路各自可信之后自然就对的。

**结论**：融合不是"锦上添花"，它负责补字面召回的短板；但融合会把**最弱那一路的缺陷
放大到排序上**。所以看到融合掉点，第一步是拆开看每一路召回了什么，而不是给两路调权重。

### 坑 2：检索粒度太细，结论和宾语被切断 ⭐

**现象**：问「本季最强的是哪部」，回答「无法确定」——但视频紧接着就说了「碧蓝之海」。

**原因**：ASR 每 2–3 秒一行：

```
06:39 本季最强的
06:40 就是它有圆圆不断的星星
06:42 碧蓝之海
```

检索只捞到相似度最高的那一行，**恰好是"结论"那半句**。

**改法**：上下文扩窗（sentence window）——命中后把同源相邻句合并（前 8 秒 / 后 20 秒）。

### 坑 3：扩窗和精排的顺序（两个都踩过）

- **必须先扩窗再 rerank**：反过来的话，「本季最强的」会因"没回答问题"被精排刷掉。
- **扩窗后要按原排名还原顺序**：否则合并按时间排序，`limit` 取到的是"最早"而不是"最相关"（hit@1 掉到 37.5%）。

### 坑 4：时间戳错位——点过去和说的不一致 ⭐

**现象**：证据显示 `00:30`，但内容（《穹庐下的魔女》）其实在 `01:30`。

**原因**：OCR 每 30 秒一帧、每帧覆盖 30 秒、**首尾相接**。扩窗用「有重叠就收」，窗口**链式合并**：

```
90秒那帧 → 82~140
60秒那帧 → 52~120  ← 重叠
30秒那帧 → 22~80   ← 又重叠
最终 30~170 秒 → 显示 00:30
```

**改法（5 层）**：
1. 只收「**起点**落在窗口内」的片段，不是"有重叠就收"
2. 窗口总长封顶 40 秒
3. 新增 `anchorMs` = 命中那一句的起点，证据时间戳和点击都用它
4. OCR 一帧本身就 30 秒，只取命中帧自身
5. **确定性兜底**：按引文原文匹配到所在片段，且**来源要匹配**（OCR 不能落到 ASR 锚点）

**效果**：证据时间戳 01:25 / 01:30 / 01:46 / 02:10 / 06:39 / 08:26 全部与原文位置一致。

### 坑 5：时间坍缩——16 分钟视频只看前 5 分钟 ⭐

**现象**：16 分钟的视频，答案只覆盖 0–7 分钟。

**诊断**：检索池其实覆盖全片（0.9–15.6 都召回了），是模型只引用前段。向量最像的永远是**开场总述**。

**试错**：先加「时间覆盖约束」（切 4 个时间桶，空桶补一条）——**治标**，模型看到的还是零散句子，它不知道自己漏了什么。

**正解**：**5 分钟分段摘要**（small-to-big）
- 每段用 LLM 生成「这段讲了什么 + 关键词」，存 SQLite `video_chunks`
- 问答时把「全片目录」同时给 Planner / Executor / Critic
- 模型先看目录，缺证据时能诚实说"这段没检索到"

**效果**：覆盖从 0–7 分钟扩展到 **0–16 分钟**，补出了 08:26《二十世纪电器目录》、15:14《再见琵琵》。

### 评价口径的三个坑

- **扩窗后 hit@K 全饱和**（28 秒窗口什么都能重叠上）→ 名次评测改用**句子级**（`search_raw` 不扩窗）
- **三种配置口径要一致** → 都扩窗或都不扩窗，不能一半一半
- **名次对了 ≠ 证据里有答案** → 单看 hit@K 会漏掉最要命的一类失败：一句「本季最强的」
  排第一名，名次满分，宾语在下一句。所以要补一个**内容级**指标（`--content`）：
  返回的文本里有没有答案关键词。

内容级评测的对照（17 题，hybrid+rerank，top-5）：

| 证据形态 | 答案覆盖率 | 完全命中 | 中位耗时 |
|---|---|---|---|
| 句子级（不扩窗） | 43.1% | 41.2% | 403ms |
| 扩窗（前 8s / 后 20s） | **94.1%** | **94.1%** | 376ms |

这条数据补上了名次指标测不到的那一半：**hit@1 94.4% 的系统，句子级证据里只有 43% 真的
包含答案**。扩窗把它拉到 94%，代价接近零（本地拼接相邻句，不多调一次模型）。

顺带一个反直觉结果：rerank 在名次口径下 18 题 0 增量（94.4% → 94.4%），但在内容口径下
把 88.2% 拉到 94.1%，代价约 170ms。**同一系统、两套口径，对"要不要 rerank"给出相反答案**——
所以报指标必须带 K、带证据形态，跨口径的数字不能直接相减。

### 评测集本身也要够用

第一版只有 8 题，一旦 hit@5 就是 100%，三档配置完全没区别，等于没有区分度。
现在扩到 18 题，覆盖三类：

- **语音题**：只在 ASR 里出现的事实（三件事、评分段、黑马靠什么）
- **画面题**：只在 OCR 里出现的事实（复联 5 回归角色、马戏盛典冠军）——用来验证 OCR 这一路是否真的起作用
- **跨模态题**：同一部作品在语音和画面各出现一次（猫与龙、弹丸论破）

18 题也还是小样本，只够看趋势、不够下强结论；这一点在 README 里写明了，不拿它当"生产级评测"。

## 五、多轮与总结

### 1. 总结不到位

**现象**：问「哪些好看」，总结是「视频把本季称为『高分旗舰之战』…」——**126 字的结构复述，没回答问题**。

**改法**：prompt 六条硬规则 + Critic 增加 summary 检查：
1. 第一句就是答案
2. （可选）用半句点出全片结构
3. ≤100 字
4. 有多个候选按强调程度排序
5. 细节留在 conclusions
6. 没答案就一句话说清

**效果**：126 字 → 55 字，直接给答案。

### 2. 多轮追问

**问题**：问完「高分作有哪几部」，接着问「那第二部呢」——检索拿到六个字，没有实体，必挂。

**改法**：`query_rewrite.py`，把追问 + 最近两轮历史改写成完整问题：
```
那第二部呢 → 《无职转生3》的评价如何
```
两个约定：**没历史/问题已自足就不改写**（省 LLM）；**改写失败用原问题**（不让链路断）。

### 3. 重复时间戳

同一时间戳出现 4 次（一个窗口里拆出多条引用）→ 前端按 `(时间戳, 来源)` **分组展示**（数据层不合并，因为每条证据绑着自己的 claim）。

## 九、交付层：鉴权 / 词表 / 一键起

### 1. 接口鉴权：认证和授权是两件事

改造前只有"登没登录"这一层（而且还没铺开），没有"这条数据是不是你的"。具体洞：

| 接口 | 问题 |
|---|---|
| `/api/ask` `/api/ask_agent` `/api/ask_agent_stream` | 未登录可调；换一个 `mediaId` 就能问别人视频的内容 |
| `/api/upload*` | 未登录可往 MinIO 灌任意文件；`uploadId` 无主，拿到就能续写别人的上传 |
| `/api/video-status` | 不校验归属，可枚举别人的解析进度 |
| `/api/videos` | 未登录时 `user_id=None` 走全量分支，能列出全站视频 |
| `/api/feedback` | 能给别人的任务打反馈 |

修法：`login_required` 装饰器 + `_require_owned_media` / `_chunk_dir_owned` 两个归属校验。
三个细节值得记：

- **越权回 404 不回 403**：403 等于告诉对方"这个 id 存在但你不配"，404 不泄露存在性，也没法拿来枚举。
- **SSE 接口的 401 必须在 `return Response` 之前**，否则错误会被包进流里发出去。
- **`uploadId` 要做格式校验**：`os.path.join(CHUNK_DIR, upload_id)` 直接拼，`../../` 能穿越到任意目录。

实测 28 个用例（未登录 / 他人资源 / 本人资源 / 非法参数）全通过，
脚本在 `scripts/verify_auth.py`，跑完自动删掉临时账号：

```bash
python scripts/verify_auth.py          # 服务已在 8001 上跑
```

### 2. ASR 词表：热词是偏置，不是保证

`data/hotwords.txt`（17 个专名）+ `data/asr_fixups.txt`（输出层纠错），
`pipeline.transcribe` 传 `hotwords=`，再对输出跑一遍纠错。

同一段 2 分钟音频、17 个目标专有名词的 A/B：

| 配置 | 命中专有名词 |
|---|---|
| 不带 `hotwords` | 2 个（碧蓝之海、再见啦啦） |
| 带 `hotwords` | 4 个（+猫与龙、+向日葵马戏团） |

两版全文差异 11.2%——**不是单调变好**，有些词变对、有些变差（"你"识别成"泥"）。两条结论：

- 热词只影响新上传的转写。命中上传去重的视频不会重跑 ASR，历史数据仍是旧结果。
- 纠错表比热词危险：一开始写了 `超版女友=碧蓝之海`，跑完 A/B 才发现那是一部和碧蓝之海
  并列的作品，不是同一个词被听错。**写错的纠错规则等于主动制造错误**，比不纠正更糟。

### 3. 一键起：容器合并 + 地址外部化

原来四个中间件是一条条 `docker run` 起来的，app 还得在宿主机跑。现在一个 compose 起全套，
带 healthcheck 和依赖顺序；whisper 模型、上传目录、SQLite 库、词表都挂卷。

真正的坑不是写 yaml，是**地址**：6 个文件把 `QdrantClient(host="127.0.0.1")` 写死了。
容器里的 `127.0.0.1` 指的是容器自己，所以必须走 `settings.qdrant_kwargs()`，
由 compose 把 `QDRANT_HOST` 注入成服务名 `qdrant`。

顺带补了两处启动容错：

- MinIO 连不上时重试 5 次，仍失败只告警不退出——否则 app 比 MinIO 先起来就崩；
- `app.run` 的 host 改从环境变量读，本地默认仍只听 `127.0.0.1`，容器里才 `0.0.0.0`。
