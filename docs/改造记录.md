# video-rag 改造记录

> 从「能跑的原项目复刻」到「有检索评测、有分段摘要、有单测」的完整记录。
> 按「遇到什么问题 → 怎么改 → 改完什么效果」组织，方便复盘和后续维护。

---

## 总览

一句话：**把一个「能问答的视频 RAG」补成了「知道自己哪里会坏、并且能量化」的系统。**

主要做了四件事：

1. **工程能力**：上传后自动解析、分片上传、健康检查、失败重试
2. **检索质量**：向量 + BM25 → RRF → 扩窗 → rerank，并量化三种配置
3. **时间准确性**：修掉了「点过去和说的不一致」的时间戳错位
4. **长视频覆盖**：5 分钟分段摘要，解决「只看前 5 分钟」的时间坍缩

## 一、环境与依赖（7 个坑）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `docker ps` 报 permission denied | 我的命令被沙箱禁了命名管道，**不是没装 Docker** | 提高权限后正常 |
| 2 | 三个中间件都没起 | 容器存在但停了 | `docker start qdrant redis minio` |
| 3 | anaconda 缺一半依赖 | 项目真正用的是 `ca-test` venv（Python 3.13） | 定位到 `run_web.bat` 里的路径 |
| 4 | `faster-whisper` 报 `metadata_errors` | `av 19` 改了 `open()` 参数，与 faster-whisper 1.2.1 不兼容 | **先用 ffmpeg 抽 16k wav，再把 numpy 数组喂给模型**，彻底绕开 av |
| 5 | `imageio_ffmpeg` 找不到 | 没装 | `_ffmpeg()` 加回退：imageio → 系统 ffmpeg → "ffmpeg" |
| 6 | Qdrant 一直 502 | **Windows 系统代理**把 `127.0.0.1:6333` 也拦了 | 把本地地址写进 `NO_PROXY` |
| 7 | 匿名上传 500 | `videos.user_id NOT NULL`，未登录时是 None | `user_id or 0` 兜底 |

> 第 4 和第 6 是最容易复发的，换机器部署时先检查这两处。

## 二、工程能力（P0）

### 1. 上传后自动解析

**问题**：原项目上传完只是存文件，要手动跑三个脚本才建索引。

**改法**：新增 `pipeline.py`，上传完成自动进后台队列：

```
上传 → 后台线程 → ASR → OCR → 向量化 → Qdrant
                    ↓
              状态写回 videos 表：转写中 → 识别画面文字 → 建向量索引 → 完成
```

- 单线程 + 队列（够用且好讲，不引入 MQ）
- 模型懒加载缓存（484MB，不能每任务重载）
- 失败写 `status=failed` + 原因，不抛给 Web 层

**效果**：前端视频列表实时显示「解析中 / 已就绪 / 失败」。

### 2. 分片上传 + 断点续传

**问题**：大视频一次性 POST 容易超时，断了要重传。

**改法**：5MB 分片，四个接口 `init / chunk / status / complete`；前端先查已传分片，**只补缺的**；每片单独重试（0.5s/1s/2s 退避）。

### 3. 健康检查 / 失败重试 / 上传去重

- `GET /health` 返回 redis / minio / qdrant 状态
- OpenAI 客户端 `max_retries=3`；Qdrant upsert 单独包一层重试
- 文件 SHA256 去重，同一视频重复上传复用已有索引

## 三、多视频隔离 + 检索评测（P0）

### 1. 按 `media_id` 过滤

**问题**：多视频时检索不隔离，问 A 会捞到 B 的证据，**时间戳跳转会跳到错的视频**。

**改法**：全链路打通 `media_id`：

```
前端 askWithVideo() → api { mediaId } → 路由 data.get("mediaId")
  → search(media_id) / run_agent(media_id) → Qdrant Filter
```

**顺手修的两个坑**：
- 缓存键要带 `mediaId`，否则 A 视频的答案会被 B 视频复用
- `/api/ask_agent` 的缓存 **get 和 set 用了不同的 key**，永远命中不了 → 统一

**数据迁移**：现有 455 个向量点 `media_id` 全是 `None`（旧脚本没写），直接加过滤会「一条都搜不到」→ 确认属于哪个视频后**回填**。

### 2. 检索层评测

**问题**：端到端评测只知道答案好不好，**定位不到是检索没捞到还是生成没写好**。

**改法**：新增 `eval_retrieval.py`，用人工标定的**黄金时间区间**单独量检索：

| 指标 | 含义 |
|---|---|
| `hit@K` | Top-K 里有没有落在正确时间区间的证据 |
| `recall@K` | 多区间被覆盖的比例 |
| `MRR` | 第一条命中证据排名的倒数 |

## 四、检索质量（P1）——这里踩了最多的坑

### 坑 1：融合不一定涨

| 配置 | hit@1 | MRR |
|---|---|---|
| 纯向量 | 87.5% | 0.875 |
| + BM25 + RRF | **75.0%** ↓ | 0.750 |
| + rerank | **100%** ↑ | 1.000 |

**结论**：单路已经很强时，BM25 的字面匹配片段会挤掉正确的 Top-1。**融合负责召回，rerank 负责定序**，只融合不精排可能更差。

### 坑 2：检索粒度太细，结论和宾语被切断 ⭐

**现象**：问「本季最强的是哪部」，回答「无法确定」——但视频紧接着就说了「碧蓝之海」。

**原因**：ASR 每 2–3 秒一行：

```
06:39 本季最强的
06:40 就是它有圆圆不断的星星
06:42 碧蓝之海
```

检索只捞到相似度最高的那一行，**恰好是"结论"那半句**。

**改法**：上下文扩窗（sentence window）——命中后把同源相邻句合并（前 8 秒 / 后 20 秒）。

### 坑 3：扩窗和精排的顺序（两个都踩过）

- **必须先扩窗再 rerank**：反过来的话，「本季最强的」会因"没回答问题"被精排刷掉。
- **扩窗后要按原排名还原顺序**：否则合并按时间排序，`limit` 取到的是"最早"而不是"最相关"（hit@1 掉到 37.5%）。

### 坑 4：时间戳错位——点过去和说的不一致 ⭐

**现象**：证据显示 `00:30`，但内容（《穹庐下的魔女》）其实在 `01:30`。

**原因**：OCR 每 30 秒一帧、每帧覆盖 30 秒、**首尾相接**。扩窗用「有重叠就收」，窗口**链式合并**：

```
90秒那帧 → 82~140
60秒那帧 → 52~120  ← 重叠
30秒那帧 → 22~80   ← 又重叠
最终 30~170 秒 → 显示 00:30
```

**改法（5 层）**：
1. 只收「**起点**落在窗口内」的片段，不是"有重叠就收"
2. 窗口总长封顶 40 秒
3. 新增 `anchorMs` = 命中那一句的起点，证据时间戳和点击都用它
4. OCR 一帧本身就 30 秒，只取命中帧自身
5. **确定性兜底**：按引文原文匹配到所在片段，且**来源要匹配**（OCR 不能落到 ASR 锚点）

**效果**：证据时间戳 01:25 / 01:30 / 01:46 / 02:10 / 06:39 / 08:26 全部与原文位置一致。

### 坑 5：时间坍缩——16 分钟视频只看前 5 分钟 ⭐

**现象**：16 分钟的视频，答案只覆盖 0–7 分钟。

**诊断**：检索池其实覆盖全片（0.9–15.6 都召回了），是模型只引用前段。向量最像的永远是**开场总述**。

**试错**：先加「时间覆盖约束」（切 4 个时间桶，空桶补一条）——**治标**，模型看到的还是零散句子，它不知道自己漏了什么。

**正解**：**5 分钟分段摘要**（small-to-big）
- 每段用 LLM 生成「这段讲了什么 + 关键词」，存 SQLite `video_chunks`
- 问答时把「全片目录」同时给 Planner / Executor / Critic
- 模型先看目录，缺证据时能诚实说"这段没检索到"

**效果**：覆盖从 0–7 分钟扩展到 **0–16 分钟**，补出了 08:26《二十世纪电器目录》、15:14《再见琵琵》。

### 评价口径的两个坑

- **扩窗后 hit@K 全饱和**（28 秒窗口什么都能重叠上）→ 评测改用**句子级**（`search_raw` 不扩窗）
- **三种配置口径要一致** → 都扩窗或都不扩窗，不能一半一半

## 五、多轮与总结

### 1. 总结不到位

**现象**：问「哪些好看」，总结是「视频把本季称为『高分旗舰之战』…」——**126 字的结构复述，没回答问题**。

**改法**：prompt 六条硬规则 + Critic 增加 summary 检查：
1. 第一句就是答案
2. （可选）用半句点出全片结构
3. ≤100 字
4. 有多个候选按强调程度排序
5. 细节留在 conclusions
6. 没答案就一句话说清

**效果**：126 字 → 55 字，直接给答案。

### 2. 多轮追问

**问题**：问完「高分作有哪几部」，接着问「那第二部呢」——检索拿到六个字，没有实体，必挂。

**改法**：`query_rewrite.py`，把追问 + 最近两轮历史改写成完整问题：
```
那第二部呢 → 《无职转生3》的评价如何
```
两个约定：**没历史/问题已自足就不改写**（省 LLM）；**改写失败用原问题**（不让链路断）。

### 3. 重复时间戳

同一时间戳出现 4 次（一个窗口里拆出多条引用）→ 前端按 `(时间戳, 来源)` **分组展示**（数据层不合并，因为每条证据绑着自己的 claim）。

## 十、一句话复盘

> 这个项目最大的收获不是"功能变多了"，而是**知道了每个环节会在哪坏**：
> 融合可能掉点、检索粒度会切断语义、扩窗会让时间戳错位、长视频会时间坍缩。
> 每一个都是**先看到坏结果、再定位、再量化验证**，而不是拍脑袋加功能。
